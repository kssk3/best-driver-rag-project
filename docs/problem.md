# 문제와 평가 기준

## 사용할 사람과 해결할 일

사용자는 서대문구와 송파구 주민이다. 품목과 배출 상황을 질문하면 공식 문서를 찾아 적용 가능한 배출 방법과 출처를 안내한다. 필요한 지역이나 조건이 빠졌으면 필요한 정보만 되묻고, 확인한 자료로 답을 뒷받침할 수 없으면 정보 부족을 알린다.

문구가 비슷한 다른 구의 규칙을 적용하거나 원문에 없는 일정과 장소를 만들어 내면 잘못된 안내가 된다. 따라서 문서를 찾는 단계와 찾은 근거로 답하는 단계를 나눠 검증한다. 검색 점수는 사실이 맞을 확률로 표시하지 않는다.

아래는 동작을 설명하기 위한 가상 예시이며 실제 분리배출 규칙이나 평가 문항이 아니다.

| 가상 문서와 질문 | 기대하는 동작 |
| --- | --- |
| 문서에 “평일 입실은 오후 6시까지”만 있고 금요일 시간을 질문 | 해당 구절을 검색하고 오후 6시까지라고 답한다. |
| 같은 문서에서 토요일 시간을 질문 | 평일 구절이 검색돼도 토요일 근거로 사용하지 않는다. 확인한 자료로 토요일 시간을 안내할 수 없다고 답한다. |

금요일 답을 맞혀도 해당 근거를 못 찾았다면 검색 성공으로 세지 않는다. 평일 구절을 찾고 토요일도 같은 시간이라고 답했다면 답변 생성의 실패다.

## 확정 범위와 구현 상태

현재 저장소는 초기 구조를 마련하는 단계다. 아래는 구현 목표와 완료 기준이며 실제 수집, 모델 호출, 지도 또는 평가가 완료됐다는 뜻이 아니다.

| 구분 | 확정된 범위 |
| --- | --- |
| 지원 지역 | 서대문구와 송파구 2개 구 |
| 자료 | 분리의 정석의 공통 품목 안내와 자치구 공식 원문, getSpot 장소 자료 |
| 화면 | Streamlit에서 질문, 응답 상태, 실제 근거, 장소 목록과 지도 표시 |
| 검색 | A Vector, B BM25와 Vector 결합, C Hybrid 후보 재정렬 |
| 최적화 | 질문 다듬기(쿼리 리라이트)의 적용 전후 비교 |
| 추가 기능 | 동 이름과 지역 해석, 장소 저장과 조회, 관찰 검증 패널 |
| 품질 추적 | Ragas 자동 평가와 Langfuse 실행 추적, 사람의 원문 검토 |

자료는 서로 다른 답변 가능 질문 25개를 뒷받침해야 하며, 유사 용어나 예외 조건으로 혼동하기 쉬운 문서 최소 2개를 포함한다. 이 25개는 구의 개수가 아니다. 장소 API 결과와 지도 표시 사례만으로 문서 기반 질문 수를 대신하지 않는다. 장소 자료가 실제로 두 구에서 제공되는지와 해당 품목을 받는지는 수집 결과로 확인한다.

Python과 LangChain 중심의 수업 환경, Selenium 수집을 사용한다. 생성 모델, 임베딩 모델, 저장소와 reranker는 실행 가능성과 이용 조건에 따라 선정한다. 외부 업무 시스템 쓰기, 결제와 발송, 모델 학습과 파인튜닝은 제외한다. 목표에 필요한 추가 구현은 허용하되 필수 결과를 우선한다.

품질, 응답 시간과 비용의 우선순위, 각 지표의 팀 목표값은 결과를 보기 전에 합의해 기록한다. 이 문서는 측정하지 않은 성능 수치나 통과율을 목표로 확정하지 않는다.

## 질문, 근거와 응답의 기준

- 원질문, 해석한 지역과 변환 질의를 구별한다. 질문 다듬기는 의도와 조건을 보존하고 실제 검색 질의에 반영한다. 변환 오류가 나면 원질문으로 검색하며, 생성기는 원질문을 기준으로 답한다.
- 지역 제한은 최초 A 검색부터 A/B/C에 공통 적용한다. 동 이름이 모호하거나 사용자가 선택한 지역과 충돌하면 임의 확정하지 않는다. 구를 알아낸 것을 행정동까지 확인한 것으로 취급하지 않는다.
- 검색 후보, 실제 생성 모델에 전달한 근거와 최종 인용을 구분한다. 인용은 실제 문서와 청크, 원문 위치에 연결한다.
- 같은 본문이라도 출처별 문서와 조건을 보존한다. 임베딩 재사용과 출처별 문서 저장을 구별하고 이전 규칙과 새 규칙이 섞이지 않게 한다.
- 장소 결과는 문서 청크와 별도 형식으로 전달한다. 문서 인용과 장소 출처를 각각 표시하며 결과 없음, 조회 오류와 좌표 누락을 구별한다. 가까운 순서에는 기준 위치가 필요하다.
- 답변 가능, 추가 조건 확인, 근거 부족과 실행 오류를 구분한다. 검색 결과에 답이 없다는 이유로 문서 전체에도 답이 없다고 단정하지 않는다.

응답 캐시는 필수 최적화가 아니다. 기존 임베딩 재사용은 별도 공통 처리이며, 최종 비교에서는 응답 캐시 효과를 배제한다.

## 평가셋과 최종 80건

| 평가셋 | 구성 | 사용할 때 |
| --- | --- | --- |
| 개발 10문항 | 답변 가능 8개, 근거 없음 2개 | 기능 개선과 설정 조정에 사용한다. 별도 관찰 질문도 최종셋과 구별한다. |
| 최종 20문항 | 직접 검색 10개, 표현 변형이나 조건 구분 7개, 근거 없음 3개 | 준비하는 시점부터 개발과 튜닝에서 분리하고, 조건을 고정한 최종 비교에 사용한다. |

문항에는 질문, 필요한 조건, 필수 사실, 허용 근거와 원문 위치, 판정 이유를 연결한다. 근거 없음 문항은 부재 판정 이유를 기록한다. **평가용 정답표와 허용 근거 목록은 검색 색인, 생성과 리라이트 입력에 넣지 않는다. 원문 문서는 정상적으로 색인하고 검색된 근거를 생성에 사용한다.** 청킹이 바뀌면 근거 매핑을 갱신한다.

| 구성 | 실행 수 | 질문 다듬기 |
| --- | ---: | --- |
| A Vector | 20건 | OFF |
| B Hybrid | 20건 | OFF |
| C Hybrid + reranker | 20건 | OFF |
| C + 질문 다듬기 | 20건 | ON |

같은 최종 20문항을 네 구성에 실행해 총 80건을 기록한다. 문서와 청크, 지역 해석, 생성 모델, 프롬프트, 출력 및 컨텍스트 제한을 동일하게 유지한다. 각 검색 구성의 방식과 설정을 기록하고, 문서/색인, 동 매핑, 별칭 사전, 모델과 프롬프트 및 설정 버전을 고정한다. 지도와 지역 인식은 별도 기능 사례로 검증한다.

## 지표와 실패 기록

| 구분 | 계산과 판단 기준 |
| --- | --- |
| Hit@5 | 답변 가능 17문항에서 허용 근거가 상위 5개 안에 하나 이상 있는 문항 수/17. 검색 실패는 0으로 계산하고 후보가 적으면 실제 개수를 유지한다. |
| 정답 충족 | 답변 가능 17문항에서 필수 사실이 정확하고 모순이 없는 답변 수/17. |
| 근거 적합 | 답변 가능 17문항에서 실제 인용이 주요 주장을 뒷받침하는 답변 수/17. |
| 근거 없음 대응 | 근거 없음 3문항에서 내용을 만들어 내지 않고 올바르게 정보 부족을 안내한 수/3. 호출 오류는 성공으로 세지 않는다. |
| 시간과 오류 | 성공 수/전체 시도 수, 성공 요청 전체 응답 시간의 평균/중앙값/표본 수, 오류와 timeout, 재시도 기록. |

Hit@5는 하나 이상의 허용 근거를 찾았는지를 나타내며, 복수 근거가 필요한 답변의 모든 근거를 확보했다는 뜻은 아니다. Hit@3은 추가 지표로 사용할 수 있다. Ragas 자동 점수는 사람의 정답 충족과 인용 적합 판정을 대체하지 않는다.

리라이트 시간은 전체 응답 시간에 포함한다. 서비스 응답과 사후 평가의 시간 및 비용은 분리하고, 비용을 보고할 때는 사용량이나 호출 횟수 등 산출 근거를 남긴다. 같은 요청의 질문, 후보와 순위, 실제 모델 입력, 답변과 인용, 상태와 오류, 버전을 추적한다. 최초 실패, 재시도와 수정 후 추가 실험은 원본을 덮어쓰지 않고 구분해 보존한다.

실패는 검색 누락, 순위 실패, 생성 오류, 잘못된 인용, 근거 없음 대응 실패로 구분한다. 표본 화면, 고정 근거를 사용한 생성 시험, 실제 검색 연결도 실행 유형으로 구별한다.

## 완료와 제출

[팀 공통 진행 단계](../ROADMAP.md)의 최종 진입 조건을 확인한 뒤 평가하고, 결과를 근거로 최종 구성을 선택한다. 다른 팀원이 README를 따라 설치, 색인 재생성, 정상 및 근거 없음 질문과 확정 기능을 실제 실행할 수 있어야 한다.

실행 코드와 README, 문서 목록과 이용 조건, 30문항과 정답 근거, 실행 원본과 비교 보고서, 실패 분석, 개인별 구현/검증/리뷰, 타인 재현, 발표자료와 시연 영상을 하나의 제출 경로에 연결한다. 최종 제출 버전은 `ax1-project3-submit` 태그로 구분한다. 관찰한 결과와 미확인한 범위를 함께 기록한다.

## 자료와 설계 참고

- [분리의 정석](https://xn--oy2b29bd3a601b.kr/front/summary/introductionWebsite.do): 공통 품목 안내의 출발점. 지역 규칙은 해당 자치구 공식 원문에서 확인한다.
- [공식 분리배출 정보조회 API](https://www.data.go.kr/data/15156866/openapi.do): getSpot 장소 자료의 출처와 제공 조건 확인.
- [Seven Failure Points, CAIN 2024](https://arxiv.org/html/2401.05856v1): 검색과 실제 생성 입력, 답변 실패를 나누는 설계 참고.
- [Searching for Best Practices in RAG, EMNLP 2024](https://aclanthology.org/2024.emnlp-main.981/): 구성별 품질과 처리 비용 비교의 참고.
- [Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)와 [Langfuse의 Ragas 연동](https://langfuse.com/integrations/frameworks/ragas): 자동 평가와 실행 기록 연결의 참고.

평가 문항 수와 실행 수는 발제 기준이며, 역할 배정과 구현 방식은 팀의 선택이다.
