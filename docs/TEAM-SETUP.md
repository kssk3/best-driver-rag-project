# 개발 환경과 공통 연결 기준

폴더와 담당 경로의 기준은 [구조와 책임](architecture.md), 목표와 평가는 [문제와 평가 기준](problem.md)에 둔다. 이 문서는 모듈을 연결할 때 함께 지킬 규칙을 정한다.

## 실행 환경

설치는 [README](../README.md)의 루트 uv 환경을 사용한다. `.python-version`, `pyproject.toml`과 `uv.lock`을 함께 확인한다. 공용 의존성을 추가할 때 관련 담당자와 실행 가능성을 확인하고 의존성 파일과 잠금 파일을 함께 갱신한다.

UI는 Streamlit으로 구현하고 공통 Python RAG 함수를 직접 호출하는 것이 목표다. 공통 파이프라인과 평가 실행기는 구현됐으며 같은 `RAGPipeline.run`을 사용한다. Streamlit은 현재 공용 의존성과 확인한 프로젝트 가상환경에 없고, `app.py`와 화면 모듈은 시작 뼈대다. 현재 터미널에서는 `scripts.search_index`로 실제 색인의 근거를 조회하고, 공통 응답 흐름은 `scripts.demo`의 합성 자동 실행으로 확인한다. 실행 방법은 [README](../README.md)를 따른다. 별도 Next.js 프론트엔드, FastAPI 진입점과 Compose 구성은 현재 필수 범위에 포함하지 않는다.

현재 저장소는 로컬 JSON 색인과 외부 호출 없는 해시 임베딩 데모를 제공한다. 제공된 전처리 자료에는 `text-embedding-3-small`을 실제 호출해 HTML/JSON 색인을 생성하고 근거 조회까지 확인했다. 실제 DB와 답변 모델은 연결되지 않았으며, 이 색인 성공은 최종 검색/답변 품질 검증과 구분한다. 선택적 임베딩 연결의 환경변수 이름은 [.env.example](../.env.example)에 있고, 다른 기능에서 필요한 변수도 비밀값 없이 함께 갱신한다.

## 공동 입출력

양석호가 인계한 공용 규격은 [현재 역할표](../ROADMAP.md#업무-분담과-인계)에 따라 변경하는 담당자와 그 결과를 사용하는 담당자가 함께 확인한다. 현재 타입은 `src/contracts.py`, 함수 연결 예시는 [최소 구현 인계](seokho-handoff.md)를 따른다. 아래는 공용 경계에서 보존해야 할 정보다.

| 전달 데이터 | 반드시 구분하거나 보존할 내용 |
| --- | --- |
| 문서와 청크 | 식별자, 본문, 원문 위치, 출처, 적용 지역과 조건, 버전 |
| 질문과 검색 질의 | 원질문, 사용자 조건, 해석한 지역, 변환 질의, 변환 상태 |
| 검색 결과 | 후보 식별자, 본문, 출처와 조건, 단계별 점수와 순위 |
| 생성 입력과 인용 | 검색 후보, 실제 모델 입력 근거, 답변에서 실제 인용한 근거 |
| 장소 결과 | 문서 청크와 별도 형식, 장소명, 주소, 좌표, 출처, 확인된 수거 종류 |
| 실행 기록 | 요청과 실행 식별자, 실행 유형, 설정과 자료 버전, 단계별 상태, 시간과 오류 |

같은 형식을 각 모듈에 복제하지 않는다. 공용 규격 변경은 호출 코드, 예시, 검증과 문서를 함께 맞춘다. 내부 파일과 함수 구성은 담당자가 정한다.

### P04 지역 해석과 답변 생성 연결

`create_runtime`의 지역 해석기로 `src.retrieval.regions.resolve_request`를, 생성기로 `make_answer_generator(draft_p04_answer, decode_conditions=decode_p04_conditions)`를 전달한다. 검색기는 순위순으로 정렬한 `SearchCandidate` 목록을 반환해야 한다. 최종 응답은 `runtime.run(request).response`에서 읽는다. [고정 근거 테스트](../tests/unit/answer_experiments/test_p04_pipeline_answers.py)는 지역 해석 결과와 검색 근거를 미리 지정해 요청·청크·인용을 검증한다. 아래 표는 연희동 질문에서 선택한 구에 따른 검색·생성 입력을 설명한다. PR #13의 [지역 전달 테스트](../tests/unit/test_pipeline_region_handoff.py)는 생성기에 전달된 구·동과 실행 기록에 보존된 원래 요청을 확인한다.

| 연희동 수거용기 색상 질문의 입력 조건 | 공통 런타임에서 확인한 결과 |
| --- | --- |
| 사용자가 서대문구를 선택 | 검색기는 서대문구로 검색한다. 생성기는 원문에 적힌 색상으로 답하고 전달받은 청크를 인용한다. |
| 질문에 연희동만 입력하고 구는 선택하지 않음 | 검색기와 생성기 모두 해석된 서대문구·연희동을 받는다. 실행 기록의 원래 요청에는 사용자가 구를 선택하지 않았다는 사실이 남는다. |
| 사용자가 송파구를 선택 | 선택한 구와 연희동에서 추론한 구가 달라 검색과 생성 전에 지역을 다시 묻는다. |

연습용 매핑표에는 동 4곳이 들어 있다. 위례동 일정 충돌은 송파구를 명시하고 근거를 고정한 별도 관찰 사례다.

## 질문, 지역과 답변

아래는 최종 서비스에 적용할 공통 요구사항이다. 현재 공통 흐름은 생성 입력의 지역/길이 제한, 실제 입력에 포함된 인용 ID 확인과 상태/오류 기록을 제공한다. 최초 검색의 지역 제한과 조건 해석, 질문 변환의 의미 보존 및 답변 판단은 각 콜백 구현에서도 충족해야 한다. 데모는 명시된 구를 확인하고 해시/단어 포함 조건으로 검색하므로 동 추론이나 실제 A/B/C 품질 구현으로 취급하지 않는다.

- 지역 제한은 A 검색부터 적용한다. 동 이름 인식이 선택한 구와 충돌하거나 행정동과 법정동이 모호하면 임의로 덮어쓰지 않는다.
- 질문 다듬기는 의미와 조건을 보존하며 변환 질의를 실제 검색에 사용한다. 변환 실패 시 원질문으로 검색하고 실패 상태를 기록한다.
- 생성기는 원질문을 기준으로 답한다. 유사한 문장을 검색했다는 사실만으로 질문의 지역이나 예외 조건까지 답할 수 있다고 판단하지 않는다.
- 상태는 `answered`, `needs_clarification`, `insufficient_evidence`, `error`를 구분한다. 실행 오류를 정보 부족 대응 성공으로 집계하지 않는다.
- 인용 ID와 URL은 실제 근거에 연결한다. 검색 후보에 있었지만 실제 모델 입력에는 없었던 자료와 답변 인용을 혼동하지 않는다.
- 장소의 수거 종류를 확인하지 않고 요청 품목을 받는다고 단정하지 않는다. 결과 없음, 조회 오류와 좌표 누락을 구분하고 기준 위치 없이 가까운 순서를 만들지 않는다.

현재 리라이트 실패 시 공통 흐름은 지역 해석기가 전달한 기존 `ResolvedQuery.search_query`로 돌아간다. 원질문 복귀 요구를 맞추려면 지역 해석기는 이 값에 원질문을 보존하고 실제 문장 변환은 리라이트 콜백에서 수행해야 한다. 실제 원질문은 `RunRecord.request`, 해석 결과는 `resolved_query`, 최종 검색 질의는 `search_query`로 구분해 기록한다.

## 자료와 기록

같은 본문도 출처와 지역 조건이 다르면 연결을 보존한다. 임베딩 재사용 기준은 본문, 모델과 관련 설정을 반영하며 출처 저장 기준과 구분한다. 청킹 후에도 표, 각주와 예외가 남아 있어야 한다.

현재 로더는 출처 목록, 실제 본문을 갖춘 공용 문서 파일과 제공된 v2 전처리 묶음을 구분한다. 일반 문서는 전체를 한 청크로 보존하고, v2 자료는 별도 청커가 조문/부칙과 표 행으로 나누며 머리글, 병합 셀과 비고를 연결한다. 두 청커 모두 길이 초과 시 임의로 자르지 않고 오류를 반환한다. 별도 조건 추출은 구현되지 않았으며, `conditions`의 빈 목록을 원문에 조건이 없다는 뜻으로 사용하지 않는다. 입력 예시와 한도, 임베딩 캐시 및 색인 교체 방식은 [최소 구현 인계](seokho-handoff.md)에 둔다.

문서와 색인뿐 아니라 동 매핑, 별칭 사전, 모델, 프롬프트와 실행 설정의 버전을 남긴다. 응답 캐시는 필수 최적화가 아니며 최종 비교에서 효과를 배제한다. 최적화 비교 대상은 질문 다듬기다.

합성 예시와 공유 가능한 작은 검증 자료는 `tests/fixtures/`에 두고 합성 여부를 표시한다. 문서 자료는 `data/`, 평가 정답은 `eval/`, 실행 결과는 `results/`로 구분한다. 수집과 색인 입력을 저장소 전체에서 자동 탐색하지 않는다. 정답표와 허용 근거 목록은 검색, 생성과 리라이트 입력에 들어가지 않으며 원문 문서는 정상적으로 색인한다.

같은 요청의 후보, 실제 입력, 답변과 인용을 연결한다. Ragas 자동 평가와 사람의 채점은 별도 기록하고, 서비스 응답 시간 및 비용과 사후 평가 시간 및 비용을 나눈다. 원본 실패와 재시도를 덮어쓰지 않는다.

현재 구현은 실행 원본 JSON과 단계별 상태/시간을 저장하고, 평가 실행기는 문항/구성별 실제 결과를 반환한다. 토큰 비용, Ragas, Hit@5와 Langfuse를 자동 계산하거나 전송하지 않는다. 이 지표/추적 모듈은 담당자 구현을 연결할 위치이며 실행 기록 저장과 구분한다.

## 연결과 검증

각 담당자는 공통 예시로 독립 구현하고 준비된 작은 기능부터 통합한다. 화면용 예시, 고정 근거 생성 시험과 실제 RAG 실행은 기록에서 구분한다. 예시 응답만 표시한 상태를 실제 검색 연결로 보고하지 않는다.

`src/validation.py`와 검증 패널은 아직 시작 뼈대다. 공용 검증 함수는 화면에 의존하지 않게 작성해 생성과 평가에서도 재사용할 수 있도록 한다. 현재 모델 타입 검사와 파이프라인의 인용 검사를 이 별도 품질 검증 기능의 완료로 보지 않는다. 검사 결과를 받아 재생성하거나 보류하는 응답 정책은 답변 생성 영역에서 결정한다. 단위 검사, 실제 외부 연동과 최종 RAG 평가는 각각 확인한 범위대로 기록하며 현재 검증 결과는 [최소 구현 인계](seokho-handoff.md#구현-경계와-검증)에 둔다.
